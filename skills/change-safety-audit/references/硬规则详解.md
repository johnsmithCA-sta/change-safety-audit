# 硬规则详解（含踩坑实例）

## 铁律一：受管文件先判定

### 什么是受管文件
删除后会被平台/宿主进程自动重建的文件。典型特征：由引导流程或初始化逻辑持有模板，内容可在历史会话轨迹中检索到，但**磁盘上没有独立的模板源文件**。

### 判定方法：实验 + 观测窗口规则

```
1. 备份当前内容到 /tmp
2. 删除文件，记录精确时刻
3. 等待 ≥ 观测窗口后 ls 复核
4. 若重建 → 受管文件，改「填回内容」而非硬删
```

### 观测窗口规则（血泪）

> 对「某机制不存在」的判定，观测窗口必须 **≥ 该机制已知最大周期**。周期未知时，只能说「X 分钟内未观测到」，**不得下否定结论**。

**踩坑实例**：删除受管文件后观察 4.5 分钟未见重建 → 下结论「删即最终解」→ 第 11 分钟文件重生，结论作废，整轮返工。

配套证据链（用于排除"自己写回"的可能）：
- 审计日志里检索该文件名，命中数
- 全盘搜模板原文，确认是否有独立模板源文件
- 核对文件 mtime 与自己的操作时刻

### 受管文件的正确处置：顺势填回，不要对抗

确认删不掉后，填入正确内容。但填回时**只写该文件独有的结构化字段**，其余用一行指针指回单一事实源，**绝不复制**主文件里的散文描述——否则制造新的双事实源，等于白做。

目标：填回后的文件应比默认模板还小。实例中 582 B 空模板 → 449 B 有效内容。

## 铁律二：验收比对 md5

文件「还在」不等于「内容没被改回默认值」。若重建逻辑是「发现为空模板/为默认则重置」，填回也会被覆盖，而"文件存在"这个检查完全验不出来。

```bash
md5 -q 文件 > /tmp/baseline_md5.txt        # 改动后立刻存档
# 等满观测窗口
[ "$(cat /tmp/baseline_md5.txt)" = "$(md5 -q 文件)" ] && echo "通过" || echo "被重置"
```

成本零，堵住推论的最后漏洞。

## 铁律三：默认不留备份

**第一步先问判据，第二步才谈命名**：这次操作可逆吗？

| 判定 | 处置 |
|---|---|
| **可逆**：改动可精确反向（整串 replace + 命中次数断言）/ 上游 git 有版本（含 reflog）/ 系统废纸篓兜底 | **不留任何副本** |
| **不可逆**：覆盖远端历史、强推、被平台重建的受管文件 | **留底，且只留一处** |

**为什么不默认留**：删了又留副本等于没删；备份若落在每会话注入的目录内，等于把注入预算乘以副本数；多份副本必然漂成双事实源。

**要留时的命名（固定名同名覆盖）**：

```
补丁/次版本 → 固定名 XXX.backup.md（同名覆盖，不写日期）
主版本     → 带版本号另存 XXX.vX.Y.Z.md（保留回退能力）
```

**最容易漏的一点：文件名必须固定。** 若沿用「版本号+日期」命名，每次都是新文件名，「同名覆盖」根本不可能发生——规则写了等于没写。

实例：某章程写了「同名覆盖不留多份」，但未定义文件名，实际每次备份仍是 `SOUL.v1.0.0.20260827.md` 这类带日期的新文件，一轮操作产生 5 个备份、50% 内容重复。

**不要 `tar` 打包归档**：打包产物本身就是又一份冗余副本，且解包才能用、极易被遗忘在磁盘上。「可回退」由可逆改动 + 上游 git 承担，不由打包承担。

**还要检查自动化**：已存在的定时任务里若写死了旧的「带日期」备份规则，会持续架空新章程。改章程后必须同步检查自动化 prompt。

## 附：四条次级规则

### 下沉前先 grep
打算把某段技术细节「下沉到 skill」之前，**先 grep 目标 skill**。很可能它已经写得比你手上的副本更完整——那就直接删副本，不用下沉。实例中这一步省掉了约一半工作量。

### 技术细节的归属
```
技术细节 → 对应 skill
项目状态 → 项目 memory
跨项目跨时间的稳定偏好 → 用户级 MEMORY.md
凭据 → 平台凭据目录（chmod 600，只留指针，如 WorkBuddy 的 `~/.workbuddy/keys/`）
运维配置 → 代码与复盘文档
```

### 时效项必须配触发机制
只标「到期日」而不设扫描触发，等于没标。要么写进自动化（每月扫一次带到期日的条目），要么写进定期审视任务。

### 一处文件改多处：替换必须「累积」，断言挡不住覆盖

**现象**（2026-09-13 实测，脚本一次改 7 处）：单进程、串行、**无任何并发**，每处都写了「命中数断言、不符就中止」，脚本全程报 OK——但**只有最后 1 处落盘，其余 6 处全部静默丢失**。

**根因**：每处 `text.replace(old, new)` 都从**同一份原始 text** 出发，写盘时只写最后一次的结果。断言校验的是「**替换前**旧串存在」，每一处都能通过——**断言挡不住这种错**。

**正确姿势**：

```python
text = path.read_text()
for old, new in edits:
    n = text.count(old)
    assert n == 1, f"命中数 {n}: {old[:40]!r}"
    text = text.replace(old, new)   # 累积：基于上一步结果
path.write_text(text)
```

**判据升级**：「断言命中次数」只证明**替换前状态对**，不证明**替换已累积生效**。凡是「一批改动 → 一次写盘」的脚本，写完必须**逐条回读新串**（用 Grep 工具），不能凭脚本自报 OK。

**同源坑的另外两种表现**：同一文件并发下发两个 Edit（两边都报成功、后写者覆盖先写者）；按下标切分再重组字符串（静默丢段 + 重复段）。三者共同点——**工具都报成功，只有回读能证伪**。
