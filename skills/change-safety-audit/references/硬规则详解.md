# 硬规则详解

> 本文只讲**怎么判定、怎么验、怎么命名**，每条规则的判据都可独立执行。

## 铁律一：受管文件先判定

### 什么是受管文件

删除后会被平台 / 宿主进程自动重建的文件。典型特征：由引导流程或初始化逻辑持有模板，内容可在历史会话轨迹中检索到，但**磁盘上没有独立的模板源文件**。

### 判定方法：实验 + 观测窗口规则

```
1. 备份当前内容到 /tmp
2. 删除文件，记录精确时刻
3. 等待 ≥ 观测窗口后 ls 复核
4. 若重建 → 受管文件，改「填回内容」而非硬删
```

### 观测窗口规则

> 对「某机制不存在」的判定，观测窗口必须 **≥ 该机制已知最大周期**。周期未知时，只能说「X 分钟内未观测到」，**不得下否定结论**。

配套证据链（用于排除「自己写回」的可能）：

- 审计日志里检索该文件名，看命中数
- 全盘搜模板原文，确认是否存在独立模板源文件
- 核对文件 mtime 与自己的操作时刻

### 受管文件的正确处置：顺势填回，不要对抗

确认删不掉后，填入正确内容。但填回时**只写该文件独有的结构化字段**，其余用一行指针指回单一事实源，**绝不复制**主文件里的散文描述 —— 否则制造新的双事实源，等于白做。

**质量判据**：填回后的文件应比默认模板**更小**。

## 铁律二：验收比对 md5

文件「还在」不等于「内容没被改回默认值」。若重建逻辑是「发现为空模板 / 为默认就重置」，填回也会被覆盖，而「文件存在」这个检查完全验不出来。

```bash
md5 -q 文件 > /tmp/baseline_md5.txt        # 改动后立刻存档
# 等满观测窗口
[ "$(cat /tmp/baseline_md5.txt)" = "$(md5 -q 文件)" ] && echo "通过" || echo "被重置"
```

成本零，堵住推论的最后漏洞。

## 铁律三：默认不留备份

**第一步先问判据，第二步才谈命名**：这次操作可逆吗？

| 判定 | 处置 |
|---|---|
| **可逆**：改动可精确反向（整串 replace + 命中次数断言）/ 上游 git 有版本（含 reflog）/ 系统废纸篓兜底 | **不留任何副本** |
| **不可逆**：覆盖远端历史、强推、被平台重建的受管文件 | **留底，且只留一处** |

**为什么不默认留**：删了又留副本等于没删；备份若落在每会话注入的目录内，等于把注入预算乘以副本数；多份副本必然漂成双事实源。

**要留时的命名（固定名同名覆盖）**：

```
补丁/次版本 → 固定名 XXX.backup.md（同名覆盖，不写日期）
主版本     → 带版本号另存 XXX.vX.Y.Z.md（保留回退能力）
```

**最容易漏的一点：文件名必须固定。** 若沿用「版本号 + 日期」命名，每次都是新文件名，「同名覆盖」根本不可能发生 —— 规则写了等于没写。

**不要 `tar` 打包归档**：打包产物本身就是又一份冗余副本，且解包才能用、极易被遗忘在磁盘上。「可回退」由可逆改动 + 上游 git 承担，不由打包承担。

**还要检查自动化**：已存在的定时任务里若写死了旧的「带日期」备份规则，会持续架空新规则。改规则后必须同步检查自动化 prompt。

## 铁律四：删除前先枚举引用面

**「源对象没了 ⇒ 这备份也没用了」是错的。** 删之前必须查清谁在引用它。

### 三条硬要求

1. **全类型检索，不得只搜 `*.md`** —— 引用常在 `.py` 的 docstring 里。

   ```bash
   rg -n "<文件名>" <工作区> <规则文件目录> ~/.workbuddy/*.md ~/.workbuddy/skills \
      --glob '!**/node_modules/**' --glob '!<大体积第三方目录>/**'
   ```

   - 还需覆盖**非文档引用面**：

     | 引用面 | 为什么危险 |
     |---|---|
     | 脚本注释 / docstring | 描述「复现 / 部署 / 还原」步骤时，路径写在注释里 |
     | 配置与 JSON | 可能只是**文本匹配词**（删了实体也不该删词，历史日志还要用） |
     | 派生数据 | 待办 / 状态文件里可能带着被删物料的文件名 |
     | 自动化 prompt | 定时任务里写死的绝对路径，删了会让自动化静默失败 |

   - 排除项要显式写出（服务端目录、生产仓库目录、历史归档目录）—— 否则大目录会把检索拖超时（实测被 SIGTERM 杀掉两次）。
2. **逐条分「活引用」与「历史叙述」** —— 指向**现存路径的指针** = 活引用，必须处理；仅仅**叙述历史**（日志、归档报告里的旧路径）= 可留，且**日志与归档一律不改写**；**别名 / 匹配词**（不是路径）通常保留。
3. **判据可证伪** —— 把「无人依赖」写成可验证断言（全类型 N 命中，其中 A 为活引用已处理、B 为历史叙述保留、C 为别名保留），不靠主观印象；**拿不准的一律列为候选上报，不并入批量执行**。

### 删除批次的正确形态

1. 逐项出**判据清单**：对象 / 体积 / 依据（可证伪）。
2. 交用户**按编号批**（不擅自扩大范围 —— 清单里常混着带硬引用的活资产，扩大执行会连锁断链）。
3. **分批执行 + 每批复核**（贴 `ls` 结果证明消失）。
4. **全类型复查残留引用** ⇒ 修连带指针（只做事实性修复：把「X 还在」改成「X 已删 + 善后说明」）。
5. 把不可恢复的损失**如实登记**到台账与日志，不装饰。

> 附带收益：引用面检索顺带做了**指针体检** —— 能查出本来就已经悬空的旧指针。

## 铁律五：改上游产物前先枚举下游消费者

**改一个中间产物（推送文案 / 报表 / 导出文件 / 配置片段）时，别只看产它的那个函数 —— 真正决定用户看到什么的是最后一环的二次加工。**

### 动手前必做

1. **穷举消费者** —— `grep -rn "<产物名>" <所有相关脚本目录>`；逐个判断是「解析正文」还是「只取文件名 / mtime」。
   - 只比对日期或新鲜度的消费者 = 安全；**解析正文的一律要先跑通验证**。
2. **对每个消费者的二次加工列出四类风险**：删改（正则清洗）、包装（染色 / 加壳）、截断（字节或字数上限）、重排序。
3. **反向设计上游文案**服从下游约束，而不是让下游适配上游：
   - 关键语义**不得写进会被清洗的结构里**（圆括号、方括号、行尾）；
   - 需要分段着色的，上游就**用换行分段**，并把分段标记设为下游可稳定识别的字样；
   - 有字节上限的（如消息体 4096B / 摘要 150 字），**把降级策略写在上游**（超长先砍次要段、保住主结论），别指望下游。
4. **验收必须是端到端 dry 跑**：拿真实输入跑完【上游生产 → 下游消费】整链并打印最终渲染结果，而不是只跑上游、看它自己的 stdout。**上游 EXIT=0 + 输出看着对 ≠ 用户收到的对。**

### 同源纪律：改「快照式」文档里的事实型论断前，用全量历史数据反证

定义类结论（「X 等于 Y」「只有两种信号」）尤其危险 —— 样本里恰好只出现一种取值时，会写得像定理。

**反证成本极低**：`glob` 全量产物 → 对目标字段做 `Counter`，一次就能看出「从未出现」。

## 附：四条次级规则

### 下沉前先 grep

打算把某段技术细节「下沉到 skill」之前，**先 grep 目标 skill**。很可能它已经写得比你手上的副本更完整 —— 那就直接删副本，不用下沉。

### 技术细节的归属

```
技术细节 → 对应 skill
项目状态 → 项目 memory
跨项目跨时间的稳定偏好 → 用户级 MEMORY.md
凭据 → 平台凭据目录（chmod 600，只留指针；各平台路径不同，以本机实际为准）
运维配置 → 代码与复盘文档
```

### 时效项必须配触发机制

只标「到期日」而不设扫描触发，等于没标。要么写进自动化（每月扫一次带到期日的条目），要么写进定期审视任务。

### 一处文件改多处：替换必须「累积」，断言挡不住覆盖

**现象**：单进程、串行、**无任何并发**，每处都写了「命中数断言，不符就中止」，脚本全程报 OK —— 但**只有最后 1 处落盘，其余全部静默丢失**。

**根因**：每处 `text.replace(old, new)` 都从**同一份原始 text** 出发，写盘时只写最后一次的结果。断言校验的是「**替换前**旧串存在」，每一处都能通过 —— **断言挡不住这种错**。

**正确姿势**：

```python
text = path.read_text()
for old, new in edits:
    n = text.count(old)
    assert n == 1, f"命中数 {n}: {old[:40]!r}"
    text = text.replace(old, new)   # 累积：基于上一步结果
path.write_text(text)
```

**判据升级**：「断言命中次数」只证明**替换前状态对**，不证明**替换已累积生效**。凡是「一批改动 → 一次写盘」的脚本，写完必须**逐条回读新串**，不能凭脚本自报 OK。

**同源坑的另外两种表现**：同一文件并发下发两个 Edit（两边都报成功、后写者覆盖先写者）；按下标切分再重组字符串（静默丢段 + 重复段）。三者共同点 —— **工具都报成功，只有回读能证伪**。
