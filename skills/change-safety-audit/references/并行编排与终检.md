# 多 agent 并行改动的编排与终检

> 定位：**执行方视角**——把一批改动分给多个 agent / 多个会话并行做时，怎么分工、怎么下指令、怎么防撞写、怎么收尾验收。
> 与 `互评判据.md` 的分工：那本回答「**要不要**拉第二意见核对」，本文件回答「**怎么**并行执行一件已经决定要做的事」。两者可叠加（先并行执行、再互评复核），但不是同一件事。

---

## 一、四条分工纪律

### 1. 按「文件」切分，不按「条目」切分

一个文件只能有一个写入者。**同一条目常横跨多文件**——按条目分会撞写，因为两个执行方会同时持有同一个文件。

- 正确顺序：先列「条目 → 涉及文件」矩阵，再按文件边界把条目**重新归并**成组。
- 例外：**风险最高的那部分由自己（主 agent）做**。要精确设计接口、要能反向验证的改动（脚本行为、协议、计算口径），交出去往往要花两倍时间验收。

### 2. 跨文件共享口径必须在每份指令里逐字写死

只要有两处以上要表达同一个常量（阈值、字段名、参数默认值、判定基准），就会漂。

- 做法：把这些口径抽成一小段「共享口径」文本，**原样粘进每一份指令**，并写明「另几组也在同步此口径」。
- 验收时**逐字比对**这几处，不看语义是否相近。

### 3. 并行 Edit 竞态是常态，不是偶发

同一文件上「读 → 改 → 写」的调用必须**串行**；不要在同一条消息里并发发两个 Edit——后写者会覆盖先写者，而**两边都可能报成功**。

- 现象：工具返回 success，回读却发现改动不在，或只落了一半。
- 对策：**每条改动后回读确认**，且回读要用能命中子串的检索工具——部分环境下 shell `grep` 会静默返回空，把已生效的改动误判为丢失。

### 4. 指令里点名硬约束，并要求对方报「没做到的」

不写就会被顺手改掉的几类：重排既有章节编号（外部有引用）、写外部署名 / 日期 / 版本号、动可写范围外的文件、把「没做」写成「已做」。

**「你没做到或有问题的地方，直说，不要美化」这道题必须问。** 这类自陈往往贡献整轮最有价值的发现（目标文件被改到破线、标题与表行数不一致、跨文件口径未同步、来源署名越界）—— 它们**只有执行方自己才会先察觉到**。

## 二、什么时候值得并行

| 值得 | 不值得 |
|---|---|
| 独立文件 ≥3 个，且改动能按文件切开 | 都在同一个文件里 |
| 组之间有顺序依赖、但能分批 | 后一步的输入取决于前一步的结论（强串行） |
| 主 agent 有余力做终检 | 没人能做终检（并行会变成几份互不知情的半成品） |

**不并行的代价是慢，乱并行的代价是返工**——后者更贵。

## 三、终检序列（只能由主 agent 做）

跨文件的事没有单个执行方能兜。固定顺序，逐项留证据：

1. **语法 / 编译** —— 所有脚本过一遍编译。
2. **门禁** —— 默认模式 + 严格模式各跑一次；并记录改动前是否就已不通过，否则会把存量问题记成新引入的。
3. **新逻辑的正 / 反 / 边界用例** —— 新增判定至少要有「该命中」「不该命中」「边界」「降级」四类用例，不能只看主用例通过。
4. **既有基线回归** —— 跑原有评测并**逐项对比**改动前后的数字（用例数 / 通过数 / 均分 / 判定）；只看「还是 PASS」会漏掉内部劣化。
5. **锚点断言** —— 涉及的章节号、编号列表、标题是否仍在位。
6. **跨文件引用断链扫描** —— 形如「某文件 §N」的引用，逐个到目标文件确认该锚点存在。
7. **残留词扫描** —— 旧表述、被替换掉的数字、被废弃的口径。
8. **红线扫描** —— 外部署名 / 来源名 / 敏感值。
9. **构建残留清理** —— 编译缓存、豁免留痕件、临时产物。
10. **逐文件核对基线 diff** —— 与改动前记录的 MD5 / 行数 / 体积对比；**这一步才能发现「某个文件根本没被改到」**。（有备份才 diff 备份，无备份则 diff 基线，**别为这一步专门造备份**。）

## 四、并行最常见的四类失败与对策

| 失败 | 对策 |
|---|---|
| **并发改同一文件**：两边都报成功，实际后写者覆盖先写者，或只落一半 | 同文件「读—改—写」一律串行重放；**每条改动后回读确认** |
| **共享口径漂移**：同一个常量在多份文件里被写成不同表述 | 共享口径抽成一段文本逐字下发；验收时**逐字比对**，不看语义是否相近 |
| **破线而不自知**：某组加内容把正文推到硬上限之上，当时没有任何自动门禁，全靠该组主动上报才暴露 | **给「会破线」的东西装自动门禁**，不依赖执行方主动说 |
| **新规则先命中自己**：新增的静态检查上线后，第一个被它命中的是本工具链自己的产物 | 新规则上线后**先拿自己跑一遍** |

> 这四类的共同点：**工具与执行方都会报「没问题」**，只有终检（回读 / 门禁 / 自查）能证伪。

## 五、与互评的衔接

并行执行完不等于可以发布。往 `互评判据.md` 的判据表过一遍：命中 ≥2 条（不可逆 / 黑盒行为 / 执行者有利害关系 / 主观取舍 / 事实可证伪）就拉第二方复核，**指令写「找出我错了的地方，每条附可验证证据」**。

执行方刚做完改动，天然属于「有利害关系的执行者」——这一步不是形式，是打破确认偏误的手段。
